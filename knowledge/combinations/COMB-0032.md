## Decision structure

The player receives exact reagent and product schemas, authors a persistent
cyclic machine program and commits it to a separate resettable run. Synchronized
execution repeatedly requests inputs and submits only exact accepted products;
a kinematic conflict halts the run. The design must survive long enough to
produce the required quota, then remains available for revision.

Both games also share `INF-001` and `OBJ-016`, but generic current-state
visibility and optional multi-metric optimisation are not causal requirements
of this exact-output execution core.

## Combination match boundary

A visual-programming game does not instantiate this combination merely by
executing symbols. It must disclose exact structured inputs and outputs, run a
persistent synchronized cyclic program separately from editing, process
recurrent sources and exact sinks, require repeated accepted products and halt
on kinematic conflict. Component placement, temporal tapes, spatial routes and
transformation triggers may differ outside this shared core.

`COMB-0032` is intentionally nested inside Opus Magnum's single-game
`COMB-0022`. The larger record additionally requires both spatial component
placement and authored mechanism tapes; this recurring core omits those Actions
because SpaceChem authors spatial paths through instructions rather than
placing the same machinery.
